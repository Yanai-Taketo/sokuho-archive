# sokuho-archive — NHKニュース速報アーカイバ

NHKが配信する **ニュース速報 (flash news) のXMLフィード** を定期的に取得し、
「いつ・どんな速報が出て・いつ消えたか」を永続的に記録するツールです。

対象フィード:

```
https://api.web.nhk/sokuho/news/sokuho_news.xml
```

速報は数分から数十分で消えてしまい、**消えた後はどこにも残りません。**
このツールは、消える前に取得して残すことを目的としています。

依存ライブラリはゼロ（Python標準ライブラリのみ）です。何年も無人で動かし続ける
ことが前提なので、将来壊れる要素をできるだけ持たない設計にしています。

---

## 1. クイックスタート

```bash
git clone https://github.com/Yanai-Taketo/sokuho-archive
cd sokuho-archive
export PYTHONPATH=src

# 1回だけ取得して記録する
python3 -m sokuho_archive once

# 記録された速報を見る
python3 -m sokuho_archive list

# 本文を検索する
python3 -m sokuho_archive search 地震
```

Python 3.9以上であれば、インストールもセットアップも不要で動きます。

## 2. 何が保存されるのか

保存先は `data/` 以下です。

```
data/
├── raw/2026/09/09/sokuho-20260909T004023Z-e5f270cc56b8.xml   ← 受信したXMLそのもの
├── events/events-2026-09.jsonl                                ← 速報の出現/更新/消滅ログ
├── latest.xml                                                 ← 最新の内容
├── state.json                                                 ← アーカイブの状態（ETag・active_eventsなど）
├── runtime.json                                               ← 死活記録（Git管理外）
└── index.sqlite3                                              ← 検索用（再生成可能・Git管理外）
```

### 2.1 `raw/` — 一次資料

**受信したバイト列をそのまま、一切加工せずに保存します。** これがアーカイブの
真実であり、他のすべてはここから再生成できます。

内容が前回と1バイトでも変われば新しいファイルを書き、変わらなければ書きません。
NHKは中身が変化したときだけファイルを更新するため、5分間隔で1年間監視しても
ファイル数は10万ではなく数千程度に収まります。

### 2.2 `events/*.jsonl` — 速報の記録

毎回の取得結果ではなく、**状態の変化（トランジション）だけ** を追記します。
1つの速報は、その生涯で最大3種類の行を生みます。

| type | 意味 |
|---|---|
| `appeared` | その速報が最初に現れた |
| `revised`  | 表示中に本文やリンクが書き換えられた |
| `cleared`  | フィードから消えた |

この3つがあれば「いつ出て、どう変わり、いつ消えたか」を完全に復元できます。
毎回1行書く方式に比べて桁違いに小さく、追記専用なので過去を書き換えず、
Gitの差分もきれいなままです。

実際の行の例:

```json
{"type":"appeared","recorded_utc":"2026-09-09T01:00:12Z","event_id":"3dae817dc7e071a6",
 "revision_id":"8ae14d575c2aaba8","category":"1","date_raw":"2026/09/09 10:00",
 "date_utc":"2026-09-09T01:00:00Z","link":"","lines":["政府　緊急経済対策を発表"],
 "text":"政府　緊急経済対策を発表","flag":"1","schema_version":1}
```

### 2.3 `state.json` と `runtime.json` を分けている理由

- **`state.json`（Git管理下）** … アーカイブそのものの状態。ETag、現在表示中の速報、
  最後に内容が変化した時刻など。**内容が変化したときだけ** 書き換わります。
- **`runtime.json`（Git管理外）** … アーカイバが生きているかどうかの記録。
  **毎回の取得ごとに** 更新されます。

分けている理由は単純で、取得の大半は「304 Not Modified」だからです。
死活記録を `state.json` に書くと5分ごとにファイルが変化し、
本当の履歴が死活コミットで埋まってしまいます。かといって内容が変化したときしか
記録しないと、**平穏な数時間と、止まっているアーカイバの区別がつかなくなります。**
分離することで、どちらの問題も起きません。

### 2.4 速報の同一性 — `event_id` と `revision_id`

速報は「不変」ではありません。表示中に文言が差し替わることがあります。
そのため識別子を2つに分けています。

- **`event_id`** … その速報の *枠*。`category` と NHK自身が付けた `date` から算出。
  表示中は何度取得しても変わらず、本文が書き換えられても変わりません。
- **`revision_id`** … その *中身*。`event_id` + `link` + 本文行から算出。
  同じ `event_id` に新しい `revision_id` が付けば「書き換えが起きた」ことを意味します。

> **なぜ `pubDate` を同一性に含めないのか**
> ルート要素の `pubDate` はNHKがファイルを書き直すたびに動きます。これを
> ハッシュに含めると、内容が同じでも書き直しのたびに「新しい速報」に見えてしまい、
> アーカイブが重複で埋まります。

## 3. 運用方法

速報は短命なので、**どれだけ細かく監視できるか** が取りこぼしの量を決めます。
用途に応じて2つの方法があります。

### 方法A: GitHub Actions（手軽・無料・ベストエフォート）

`.github/workflows/archive.yml` が5分ごとに動き、変化があればコミットします。
サーバーを用意する必要がありません。

**制約を正直に書いておきます。** GitHubのcronは実行時刻を保証しません。
混雑時には数分〜数十分遅れることも、スキップされることもあります。
速報は通常10分以上フィードに残るため多くは捕捉できますが、
**確実に全部を取る仕組みではありません。**

有効化するには、リポジトリの Settings → Actions → General → Workflow permissions で
**Read and write permissions** を許可してください。

1回の実行内で複数回取得して精度を上げることもできます（Actionsの画面から
`max_runtime` に秒数を指定して手動実行）。ただしその秒数だけランナーを占有します。
publicリポジトリなら無料ですが、**privateリポジトリでは課金対象の実行時間を消費する**
ため、承知のうえで使ってください。

### 方法B: 常駐デーモン（取りこぼしを最小化）

常時稼働するマシン（VPS、自宅サーバー、Raspberry Piなど）があるなら、
60秒間隔で回し続けるのが最も確実です。

```bash
python3 -m sokuho_archive watch --interval 60
```

systemdユニット・Dockerfile・docker-composeを `deploy/` に用意しています。

```bash
sudo cp deploy/sokuho-archive.service /etc/systemd/system/
sudo systemctl enable --now sokuho-archive
```

```bash
docker compose -f deploy/docker-compose.yml up -d
```

> 取得間隔の下限は30秒です。フィードには `Cache-Control: max-age=60` が付いており、
> 60秒より短い間隔で叩いても新しい内容は返ってこず、負荷をかけるだけだからです。

### 方法C: 併用

両方動かしても壊れません。`data/.lock` による排他制御があるため、
同時書き込みで壊れることはありません（後から来た方が黙って譲ります）。

## 4. 「動いているのに何も記録されていない」を防ぐ

このシステムで最も危険な壊れ方は、**静かに死ぬこと** です。
URLが変わったりWAFに弾かれたりしても、
「速報が無い平穏な日」と見分けがつきません。

対策を2つ入れてあります。

1. **`status` コマンドが古さで落ちる** — 最後に取得が成功してから時間が経ちすぎていると
   終了コード3を返します。

   ```bash
   python3 -m sokuho_archive status --stale-hours 3
   ```

   ここで見ているのは「最後に **取得に成功** した時刻」であって
   「最後に速報が出た時刻」ではありません。304が返り続けている状態は正常なので、
   何時間速報が無くても `healthy` のままです。Dockerの `HEALTHCHECK` はこれを使っています。

   なお、CIの実行のようにチェックアウト直後で `runtime.json` が存在しない場合は、
   コミットされているハートビートで代用します。そのため
   **リポジトリを対象に判定するときは `--stale-hours` をハートビート間隔より
   大きくしてください**（既定値は3時間と6時間なので、その用途では調整が必要です）。

2. **ハートビート** — 何も起きない時間が続いても、既定で6時間に1回は
   `state.json` に生存記録を書き、コミットさせます。これにより、
   リポジトリの履歴を見るだけで「速報が無かった」のか
   「アーカイバが止まっていた」のかを区別できます。

また、取得に失敗すると `once` は終了コード1で落ちるので、
GitHub Actionsのジョブが赤くなり通知が飛びます。

## 5. コマンド一覧

| コマンド | 用途 |
|---|---|
| `once` | 1回取得して記録する（cron向け） |
| `watch --interval 60` | 常駐して取得し続ける |
| `watch --max-runtime 240` | 指定秒数だけ回して終了する（CI向け） |
| `status` | 稼働状況を表示。古ければ終了コード3 |
| `verify` | アーカイブの整合性を検査する |
| `list -n 20` / `list --active` | 記録された速報を一覧する |
| `search 地震` | 本文を検索する |
| `stats` | 件数・期間・カテゴリ内訳を表示する |
| `export --format csv\|json` | 全件を書き出す |
| `reindex` | 検索用インデックスを再生成する |

終了コード: `0` 成功 / `1` 失敗 / `2` 引数誤り / `3` 古い・異常。

## 6. 設計上の判断

実装するうえで実際に検証したうえで決めたことを残しておきます。

**受信したものが本物かを必ず確認する。**
HTTP 200であっても、WAFのエラーページやCDNの障害ページが返ることがあります
（開発中に実際に遭遇しました。しかも `ETag` と `Last-Modified` 付きで）。
これを記録してしまうと「NHKが何も出していない」と区別できません。
そこで、空でない・サイズ上限内・`<!DOCTYPE` を含まない・整形式XMLである・
ルート要素が本当に `<flashNews>` である、をすべて満たしたものだけを記録します。

**`<!DOCTYPE` を無条件で拒否する。**
NHKはDOCTYPEを送りません。一方、内部実体参照は増幅攻撃の入口になります
（検証したところ450バイトの文書が1MBに展開されました）。
新しいCPythonには増幅の上限がありますが、それに頼ると安全性がバージョン依存に
なるため、入口で落としています。

**全文検索にFTS5を使わない。**
日本語は分かち書きしないため、FTS5の標準トークナイザは
`東北地方で震度６強の地震` を1トークンとして索引し、`MATCH '地震'` は
**エラーも出さずに0件を返します。** `trigram` トークナイザでも2文字の検索語は
救えません。実測で確認したうえで、常に正しい `LIKE` による部分一致に統一しました。
年に数千件という規模では速度差は問題になりません。

**`lines` は必ず配列のまま保存する。**
表示用の `text` は全角スペース (U+3000) で連結していますが、これはあくまで
便宜的なものです。`revision_id` は改行区切りで算出しているため、
連結方法を将来変えても同一性は揺らぎません。

**未知の要素・属性を捨てない。**
NHKがフィールドを増やしても、`extra_attrs` / `extra_children` として
記録側にも残ります。生XMLにも当然残ります。

**死活記録とアーカイブ状態を別ファイルにする。**
取得の大半は304です。死活記録を毎回コミット対象のファイルに書くと履歴が
死活情報で埋まり、逆に内容変化時しか書かないと平穏な時間帯と障害の区別が
つきません。実際、開発中にこの取り違えで「1時間おきに健全なコンテナが
再起動される」不具合を作り込み、テストで検出しました。

**SQLiteをGitに入れない。**
バイナリで差分が読めず、コンフリクトも解けません。`reindex` で
いつでも数秒で再生成できるため、`.gitignore` に入れてあります。

## 7. 制限事項

- **完全性は保証できません。** 取得間隔より短命な速報は原理的に取りこぼします。
  GitHub Actions運用では特にそうです。取りこぼしを減らしたい場合は方法Bを使ってください。
- **過去に遡ることはできません。** フィードは現在の状態しか返さないため、
  アーカイブは動かし始めた時点から積み上がります。
- 本ツールはNHKとは無関係の非公式なものです。

### 取り扱いについて

速報の見出しはNHKの著作物です。このリポジトリが保存するのは
**一次資料としての受信データとその記録** であり、再配布のためのものではありません。
公開リポジトリで運用する場合は、出典がNHKであることを明示し、
過度な取得を避けてください（既定の設定はこれを満たすようにしてあります）。

- 既定の取得間隔は60秒以上（フィードのキャッシュ指示と同じ）
- 条件付きGET（`If-None-Match`）により、変化が無ければ本文を転送しない
- 連絡先URLを含む `User-Agent` を送信
- 失敗時はジッター付き指数バックオフで待機

## 8. 開発

```bash
PYTHONPATH=src python3 -m unittest discover -s tests -v
```

`tests/fixtures/` には、実際に取得したXMLに加えて、
BOM付き・実体参照・CDATA・名前空間・打ち切り転送・Shift_JIS誤申告・
WAFのJSONエラー・増幅攻撃といった異常系のサンプルを置いてあります。

CI (`.github/workflows/ci.yml`) は Python 3.9 と 3.12 でテストを実行し、
さらに `verify` によりアーカイブ自体の整合性も検査します。
